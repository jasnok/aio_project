# 1팀 발표 대본 초안

전체 발표 시간 20분을 기준으로 한 README 진행 순서입니다. 실제 시연 속도에 따라 각 구간을 10~20초 줄일 수 있습니다.

## 0:00~0:40 — 제목과 한 문장 소개

> 안녕하세요. 1팀의 공공임대 및 분양 청약 통합 안내 서비스입니다. 저희 서비스는 여러 기관에 나뉜 청약 공고를 관리자가 검증해 같은 형식으로 정리하고, 사용자가 마감일과 주거비용을 빠르게 비교하도록 돕는 웹 서비스 MVP입니다.

## 0:40~2:30 — 문제 정의

> 청약 정보는 LH청약플러스, SH인터넷청약시스템, 청약Home, 마이홈포털 등 공급기관과 주택유형에 따라 여러 곳에 나뉘어 있습니다. 각 사이트는 공식 신청과 상세 안내에 꼭 필요하지만, 여러 기관의 공고를 한 번에 비교하려면 사용자가 사이트와 첨부 문서를 반복해서 확인해야 합니다.

> 특히 신청기간, 면적, 모집인원, 보증금과 월세의 표현이 공고마다 다르고 상세 정보가 PDF나 HWP에 포함되기도 합니다. 그래서 저희는 공식 사이트를 대체하는 대신, 공식 원문을 출처로 남기면서 비교에 필요한 항목을 표준화했습니다.

전환 멘트:

> 그러면 이 문제를 시스템에서 어떻게 나누어 해결했는지 설명드리겠습니다.

## 2:30~5:00 — 시스템 아키텍처

> 프런트엔드는 역할에 따라 관리자와 사용자 Streamlit 앱으로 분리했습니다. 두 화면은 하나의 FastAPI 백엔드를 사용합니다. 사용자 회원가입과 로그인은 Supabase Auth가 직접 담당하고, FastAPI는 청약정보와 서비스 데이터를 처리합니다.

> 정형 데이터는 Supabase PostgreSQL, 이미지 파일은 Supabase Storage에 저장합니다. 이렇게 파일과 관계 데이터를 분리해 DB에는 이미지 URL과 순서만 남겼습니다.

> 배포 환경은 사용자·관리자 Streamlit Community Cloud, FastAPI는 Render, DB·인증·Storage는 Supabase 구성을 목표로 했습니다.

## 5:00~7:30 — 데이터베이스 설계

> listings의 한 행은 주택 하나와 신청유형 하나입니다. 같은 공고라도 주택형과 면적, 금액이 다르면 비교 가능한 별도 행으로 저장합니다.

> 면적과 모집인원은 0보다 커야 하고, 보증금과 월세는 0 이상이어야 합니다. 신청 종료일이 시작일보다 빠르지 않도록 DB 제약조건도 두었습니다.

> 처음에는 listings의 image_url 한 칸에 대표 이미지 한 장만 저장했습니다. 하지만 위치도, 평면도, 외관을 함께 보여 주기 위해 listing_images를 1:N으로 분리했습니다. sort_order 0이 대표 이미지이며, 공고가 삭제되면 연결 행도 Cascade로 삭제됩니다. 실제 파일은 Storage에 저장하고 최대 20장까지 관리합니다.

전환 멘트:

> 다음은 이 데이터 구조가 실제 화면 편의 기능으로 어떻게 연결되는지 보여 드리겠습니다.

## 7:30~14:30 — 기능 시연

### 사용자 화면

> 사용자 목록에는 신청 종료일까지 남은 기간을 D-day로 표시했습니다. 이미 마감된 공고는 삭제하지 않고 흐리게 표시한 뒤 목록 뒤로 보내, 현재 신청 가능한 공고를 먼저 볼 수 있습니다.

> 면적은 제곱미터와 약식 평수를 함께 보여 주고, 긴 원 단위 금액은 쉼표와 억·만 단위로 표시했습니다.

시연:

1. D-day와 마감 카드 확인
2. 보증금 낮은 순 선택
3. 면적 넓은 순 선택
4. 2페이지 이동 후 새로고침
5. 이미지 갤러리와 공식 원문 링크 확인

### 관리자 화면

> 관리자는 공식 공고를 확인해 표준 항목과 이미지를 등록합니다. 같은 공고의 여러 주택형을 반복 등록하는 경우가 많아, 등록 후에는 입력값을 유지하고 필요할 때만 초기화하도록 만들었습니다.

> 조회 화면에서는 현재 페이지의 공고를 전체 선택하거나 일부만 선택해 삭제할 수 있습니다. 삭제 전에 대상 이름과 건수를 확인하고, 결과는 성공과 실패로 나누어 보여 줍니다.

시연:

1. 금액 입력 보조와 이미지 여러 장 선택
2. 등록 후 값 유지
3. 입력 초기화
4. 현재 페이지 전체 선택과 일부 해제
5. 삭제 확인창까지만 진행하거나 삭제 전용 가짜 공고 삭제

## 14:30~17:30 — 담당 업무와 개발 방식

> 제가 담당한 범위는 관리자 청약정보 등록, 관리자 조회·삭제, 사용자 청약정보 조회입니다. 이를 위해 listings와 listing_images를 설계하고, 다중 이미지 Storage 연동, D-day, 페이지네이션, 평수·금액 표시, 10가지 정렬, 등록 폼 상태 유지, 선택 삭제를 구현했습니다.

> 작업은 기능마다 GitHub Issue로 문제와 완료조건을 정의하고, 별도 브랜치에서 구현과 테스트를 진행했습니다. 이후 Pull Request 검토를 거쳐 develop에 병합하고 Issue를 종료했습니다. main은 직접 수정하지 않았으며 최종 검토가 끝난 시점에 develop을 반영하는 전략을 사용했습니다.

## 17:30~19:00 — 예외 처리와 한계

> 정상 화면뿐 아니라 검색 결과 없음, 잘못된 정렬, 없는 공고, 이미지 형식·크기 오류, 삭제 일부 실패도 구분해 안내하도록 했습니다.

> 현재는 관리자가 공고를 수동으로 입력하는 버전이고, 보증금과 월세 중심의 공공임대 스키마입니다. 분양 공고를 더 정확히 지원하려면 분양가와 공급유형을 별도 컬럼으로 확장해야 합니다.

> 또한 관리자 백엔드 API에는 실제 토큰 인증을 추가해야 공개 운영이 안전합니다. 이미지 업로드와 공고 등록이 두 요청인 부분도 임시 업로드나 보상 삭제 방식으로 개선할 계획입니다.

## 19:00~20:00 — 마무리

> 저희 서비스의 핵심은 공식 정보를 대신 판단하는 것이 아니라, 사용자가 공식 원문에 도달하기 전 비교와 탐색에 쓰는 시간을 줄이는 것입니다. UI, FastAPI, DB, Storage를 연결해 등록부터 조회와 삭제까지 동작하는 통합 MVP를 구현했습니다. 감사합니다.
