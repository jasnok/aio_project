# 청약 서비스 AI 실행 구조와 개선 기준

## 현재 프로젝트 분석

이 프로젝트의 목적은 청약 공고를 등록·조회하고 상담을 제공하는 것입니다. FastAPI `BE/app/main.py`에 사용자·관리자 API 라우터가 붙고, `FE_User/app.py`와 `FE_Admin/app.py`의 Streamlit 화면이 API를 호출합니다. Supabase는 인증·공고·사진·영구 요약을, Redis는 진행 중인 상담을 담당합니다. 설정은 앱별 `core/settings.py`와 `housing_config.Settings`를 사용하며 환경변수, 앱 `.env`, 배포 secrets, 기본값 순서로 읽습니다. 실제 값은 문서·오류 응답에 포함하지 않습니다.

기존 프로젝트에 별도 Agent registry, LangGraph Workflow, MCP 서버는 없습니다. Gemini를 호출하는 역할은 상담 답변, 상담 요약, 사이트 안내원 분류, 관리자 공고 추출·이미지 식별입니다. 이 역할들이 모두 하나의 멀티에이전트 흐름으로 연결된 것은 아닙니다. 기존 서비스·스키마·순수 검증 함수의 책임을 명확히 하고, 실제 의존관계가 필요한 기능을 확인한 뒤에만 더 복잡한 실행 구조를 고려합니다.

| 기능 | 기존 실행 흐름 | 결과 검증·저장 |
|---|---|---|
| 상담 | `/chat/message` → Redis 기록 조회 → `create_chat_answer` → Gemini 또는 명시적 mock | `ChatAnswer` → `ChatMessage` → Redis 질문·답변 저장 |
| 요약 | `/chat/save` → Redis 전체 기록 → `create_chat_summary` → Gemini JSON 또는 mock | `ChatSummaryDraft` → 서버가 ID·소유자·시간 추가 → `ChatSummaryItem` 저장 → snapshot이 같을 때만 진행 기록 삭제 |
| 사이트 안내원 | `/ai-guide` 라우터 → `classify_question` | `GuideClassification` → confidence·category 분기 → 고정 사이트 사용법 또는 짧은 답변 |
| 공고 자동 등록 | 관리자 문서 업로드 → 문서·이미지 준비 → 공고 추출·이미지 식별 동시 실행 → 사람의 결과 검토 | `validate_extracted`의 필수값·숫자·날짜·자치구 검사 → 기존 등록 API의 Pydantic 검사 → DB 원자 저장 |
| 생활권 분석 | 공고 후보 DB 검색 → 선택 주소 좌표 조회 → 지하철·마트·병원 동시 조회 | 기존 위치 스키마 → 지도. 상세주소 누락이나 필수 시설 조회 실패는 정상 분석으로 저장하지 않음 |

상담 응답에는 최근 `CHAT_HISTORY_LIMIT`개 메시지만 전달합니다(기본 10, 최대 30). 요약은 Redis에 현재 보관된 전체 기록을 전달합니다. Redis 보관 상한은 `CHAT_HISTORY_MAX_MESSAGES`(기본 30), TTL은 기본 1시간입니다. 따라서 “전체 기록”은 무제한 상담 이력이 아닙니다. `ChatRequest.messages`는 호환용 입력이며 상담 문맥은 서버의 사용자별 Redis 기록을 사용합니다.

관리자 자동 등록은 문서와 이미지 분석이 독립적이어서 두 작업을 동시에 실행합니다. 상담 답변은 기록 조회에 의존하고, 요약 후 기록 삭제는 저장 성공에 의존하므로 해당 단계는 순차 실행합니다. 화면에는 사용자 세션 상태만 두고, 권한은 백엔드에서 로그인 토큰·소유자 검사로 확인합니다.

## 참고 수업 자료와 선택

로컬 참고 폴더 `C:\aidevs`, `C:\mini_multi_agent`의 디렉터리를 탐색하고 현재 문제와 관련된 구조화 출력·Pydantic 검증·일반 Python/그래프 비교·실패 추적 예제, Role/Task/Contract 프로젝트의 계약과 Agent runtime을 선별해 읽었습니다. 수업의 여행·고객지원 코드를 프로젝트로 복사하지 않았습니다.

- `05_llm-agent-orchestration/02_prompt-and-structured-output/07_pydantic_validation.py`: 계약에 없는 값과 잘못된 자료형을 검증하는 원칙을 상담 요약 경계에 적용했습니다.
- `mini_multi_agent_02_role_task_contract/backend/app/schemas/contracts.py`, `agents/runtime.py`: 역할 출력 검증이 끝나기 전에 다음 처리로 전달하지 않는 원칙을 적용했습니다.
- `06_langgraph-workflow/09_python_vs_langgraph.py`: 현재의 짧은 순차 흐름은 일반 Python 서비스·라우터로 유지합니다. 프레임워크 도입 자체를 개선으로 보지 않습니다.
- `08_agent-evaluation-and-tracing/04_trace_failure.py`: 단순한 전체 실패 대신 원인을 구분하는 원칙을 참고합니다. 현재는 `service`·`code` 오류 응답과 요청 로그가 있으며 Agent별 영구 trace 시스템은 구현하지 않았습니다.

## 출력 계약 보완: 문제 → 변경 → 검증

기존 `ChatAnswer.answer`에는 저장용 `ChatMessage.content`의 4,000자 상한이 없었습니다. 모의 답변 4,001자는 생성 응답으로 만들어졌지만 저장 모델에서는 거절됐습니다. 답변 계약에 같은 상한과 공백 검증을 적용하고, 위반은 HTTP 502 `gemini/invalid_response`로 처리합니다. 4,000자는 저장 가능함을 확인하며 긴 답변을 임의로 잘라 내용을 바꾸지 않습니다.

기존 요약 생성은 JSON의 `title`·`summary`에 `str()`을 사용했습니다. 객체·배열도 문자열로 바뀌어 통과했습니다. `ChatSummaryDraft`는 엄격한 문자열 계약이며 알 수 없는 필드를 거부합니다. 제목은 기존 호환성을 위해 생략 가능하고, 비어 있으면 요약에서 제목을 만듭니다. 요약은 필수이고 공백 제거 후 비어 있으면 거절합니다. Gemini에는 JSON MIME과 같은 Pydantic 응답 스키마를 전달하고 반환 후 다시 검증합니다. 저장 ID·사용자 ID·시간은 모델 응답을 믿지 않고 서버가 생성합니다.

구조 검증은 문자열·필수 필드·상한·JSON 형태를 검사합니다. 이 검사는 청약 자격이나 답변 사실의 정확성을 검증하지 않습니다. 실제 공고의 숫자·날짜·자치구 의미 검증은 관리자 추출 검증과 등록 스키마가 담당하고 사람의 검토를 유지합니다. 상담 사실 검증·근거 인용·신청 자격 판단은 현재 구현 범위가 아닙니다.

Gemini 상담·안내원 클라이언트에는 HTTP 요청 제한 30,000ms와 SDK 시도 횟수 1회를 지정합니다. 사용자 화면의 45초 대기와 비교해 호출 경계를 명시하고 SDK의 기본 재시도 누적을 피합니다. 이 HTTP 제한은 Redis·DB 등 전체 Workflow의 30초 완료를 보장하지 않습니다. 설정 오류·호출 한도·시간 초과는 기존 오류 분류를 유지합니다. 실패를 실제 답변처럼 mock으로 대체하지 않으며 mock은 실행 전에 명시적으로 선택하는 시연 모드입니다.

검증은 실제 Gemini 호출 대신 모의 provider, FastAPI TestClient, 설치된 SDK와 HTTP MockTransport를 사용합니다. 거절된 답변은 Redis에 추가하지 않고, 거절된 요약은 저장하거나 진행 기록을 삭제하지 않음을 확인합니다. 실제 Provider의 스키마 지원·정확도·지연 시간 검증과 구분합니다.

## 확인된 후속 과제

- 상담 종료가 이미 진행 중인 LLM 요청을 취소하는 기능은 아직 없습니다. 같은 요청 ID가 동시에 생성 중이면 복수 LLM 호출이 발생할 수 있습니다. Redis와 요약 DB는 하나의 트랜잭션이 아니며 클라우드 동일 요청 경쟁의 완전한 단일 실행을 보장하지 않습니다.
- 관리자 이미지 분석의 실제 정확도와 PDF 크기별 처리 시간은 아직 측정하지 않았습니다. 모의 시간 초과·잘못된 출력 검증과 구분해서 평가해야 합니다.
- 상담 답변·요약의 단계별 추적은 기존 관리자 로그로 확인합니다. 안내원·공고 추출까지 같은 추적을 확장하는 작업은 아직 하지 않았습니다.
- 실제 공고·Gemini를 평가하지 않은 상태에서 “정확한 청약 판정”, “검증된 멀티에이전트 시스템”으로 소개하지 않습니다. 로컬 시연과 모의 계약 검증은 별도로 표시합니다.

전체 테스트 명령과 실행 환경은 기존 CI·`scripts/run_tests_offline.py`를 재사용합니다. 성능 수치는 별도 [성능 측정 기록](baselines/2026-10-01-performance.json)에 실제 측정 조건과 함께 남겨져 있습니다.

## 동시 요청의 기록 보존

내용 비교만으로는 빈 대화 조회 → 종료 → 늦은 답변 저장을 구분하지 못해 기록이 다시 생겼습니다. Redis 내부 상태를 `ChatHistorySnapshot(revision, messages)`로 저장하고 변경마다 UUID revision을 교체합니다. 질문·요약 라우터는 조회 시 revision을 전달해 WATCH 안에서 현재 상태와 비교합니다. 종료와 요약 정리에도 메시지 없는 revision을 같은 TTL로 보관합니다. 모델 요청을 취소하는 기능은 아니며 종료 전 생성한 답변의 늦은 저장을 차단하는 기능입니다. 같은 내용을 가진 새 대화도 다른 revision이므로 오래된 요약 정리가 삭제하지 않습니다.

과거 JSON 목록은 그대로 읽고 다음 변경 때 새 내부 형식으로 전환하며 API의 메시지 목록은 유지합니다. revision은 모델 문맥·외부 응답에 포함하지 않습니다. 내부 저장 형식이 바뀌므로 기존 버전과 새 버전의 백엔드를 혼합 실행하지 않고 모두 재시작해야 합니다. 빈 revision도 TTL 뒤 만료되므로 영구 종료 이력은 아닙니다. 특히 첫 빈 기록의 revision이 없던 요청을 TTL보다 오래 보류한 경우까지 종료 보호를 보장하지 않습니다.

이전 Redis 기록 추가는 get → 전체 기록 set이었습니다. 두 스레드의 조회를 같은 snapshot으로 맞춰 실행하면 질문·답변 4개 중 2개만 남았습니다. 지금은 WATCH → 조회·검증 → MULTI → 저장 → EXEC를 사용하고, 충돌한 Redis 변경만 최대 3회 다시 시도합니다. LLM 호출은 다시 실행하지 않습니다. HTTP 상담 라우터는 답변 생성에 사용한 기록도 함께 전달합니다. 생성 중 문맥이 바뀌었다면 새 답변을 기록에 섞지 않고 409로 안내합니다. 사용자는 ‘진행 대화 새로고침’으로 최신 기록을 확인한 뒤 재질문할 수 있습니다.

요약 생성 전 읽은 기록과 현재 기록이 같을 때만 삭제합니다. 요약 중 기록이 바뀌었다면 전체 진행 기록을 보존하고 `ChatSummarySaveResult.remaining_messages`로 반환합니다. 화면은 이 기록을 다시 표시합니다. 새 API는 기존 요약 필드를 유지하며 저장 모델은 기존 `ChatSummaryItem`을 사용합니다. 반환용 남은 기록은 요약 DB에 저장하지 않습니다.

실제 로컬 Redis에서는 두 요청의 메시지 4개가 모두 남고, 변경된 snapshot의 메시지 6개가 보존되며, 동일한 snapshot의 메시지가 정리됨을 확인했습니다. 종료 후 늦은 저장 거절과 같은 내용의 새 대화 보존도 확인했습니다. UUID 임시 키를 사용하고 정리했습니다. 재현 명령은 저장소 루트에서 `BE/.venv/Scripts/python.exe BE/scripts/verify_chat_concurrency.py`이며 Redis 주소는 로컬 시연용 `127.0.0.1:16379`로 제한합니다. 자동 테스트는 모의 WATCH 충돌·재시도 상한·TTL·보관 상한·라우터·화면 복원을 검사하고, 실제 Redis 검증과 구분합니다.

## 필수 공고 추출과 선택 이미지 식별의 실패 경계

이미지 식별은 원래 실패해도 공고 검토를 계속하는 선택 기능입니다. 하지만 숫자 `house_name` 응답은 오류 처리 밖의 `.strip()`에서 실패했습니다. `core/image_label.py`의 `ImageLabel`은 문자열·기존 프롬프트의 7개 이미지 종류를 검사하며, 잘못된 항목만 빈 라벨로 바꿉니다. 입력 이미지 개수와 순서를 유지하고 없는 항목은 빈 라벨로 채웁니다. 정상 라벨도 해당 주택의 사진이라는 사실이 검증된 것은 아니므로 관리자 검토를 유지합니다.

관리자 공고 Gemini HTTP 제한은 60초, 선택 이미지 식별은 30초입니다. SDK 시도는 각각 1회이며 앱의 공고 재시도만 2초 후 한 번 허용합니다. 상태 코드 500·502·503·504만 자동 재시도하고 429·인증·잘못된 JSON·시간 초과는 즉시 안내합니다. 원본 오류 문자열의 숫자를 재시도 판단에 사용하지 않습니다. 두 번의 실제 HTTP 시도에 각각 제한이 있으므로 전체 문서 처리 60초 완료를 보장하지 않습니다.

클라이언트는 context manager로 정리합니다. 선택 이미지 호출·JSON 해석이 실패하면 빈 라벨을 반환하며 모델 호출을 자동 반복하지 않습니다. 모의 provider로 호출 횟수, HTTP 옵션, 성공·실패 시 정리, 잘못된 라벨 fallback을 확인했습니다. Gemini SDK 1.75.0과 Pydantic 2.13.4는 실제 검사한 관리자 환경 버전으로 고정합니다. 측정하지 않은 토큰 수·시간 절반·비용 감소 주장은 코드 주석에서도 제거했습니다.

## 부분 저장 실패 후 재시도

요약 저장과 Redis 정리는 서로 다른 저장소의 작업입니다. 기존에는 요약 저장 후 Redis 정리가 실패하면 다음 요청이 새 UUID로 같은 요약을 저장했습니다. 이를 재현해 첫 응답 503·재시도 200 이후 요약 2건이 남는 것을 확인했습니다.

사용자 화면은 저장 요청마다 UUID `request_id`를 만들고 실패한 같은 요청의 재시도에 유지합니다. 새 질문·대화 갱신·종료·저장 성공·사용자 전환에서는 초기화합니다. 서버는 이 ID를 기존 요약 UUID 기본키로 사용하고, 이미 저장된 본인 요약이면 생성 없이 반환합니다. 복구 시 현재 진행 기록을 삭제하지 않고 `remaining_messages`에 담아 화면에 복원합니다. 기본키를 재사용하므로 DB 스키마 변경은 없습니다. 요청 ID가 없는 기존 클라이언트는 기존 동작으로 호환되며 재시도 중복 방지를 보장하지 않습니다.

미리보기 저장은 같은 사용자·ID 항목을 lock 안에서 중복 삽입하지 않습니다. Supabase 조회는 요약 ID와 사용자 ID를 함께 검사하고 기존 UUID 기본키가 중복 행을 막습니다. 이미 저장된 결과를 복구하는 경우의 생성 호출 감소만 검증했으며, 동시에 생성 중인 요청의 단일 LLM 호출까지 보장하지 않습니다.

실제 로컬 Supabase에서 요약 저장 뒤 Redis 정리 오류를 모의로 주고 같은 ID로 재시도했습니다. 첫 503·재시도 200, 저장 1건, 생성 1회, 진행 메시지 2개 보존, 다른 소유자 조회 없음이 확인됐습니다. 임시 Auth 계정·요약을 정리하고 기존 공고 15건을 유지했습니다. 실제 Gemini는 호출하지 않았습니다.

## 백엔드 Provider 수명 관리

상담 답변·요약·안내원은 기존 `get_gemini_client()`로 호출 시 클라이언트를 만들되 `contextlib.closing`으로 요청 범위에서 정리합니다. 성공·시간 초과·잘못된 결과 모두 close가 호출됨을 모의 클라이언트로 검사했습니다. 역할마다 클라이언트를 만든다는 기존 선택은 유지하며, 프로세스 전체의 새 공유 Provider registry는 만들지 않았습니다. 실제 연결 누수량·성능 개선 수치를 측정한 작업은 아닙니다.

안내원의 문자열이 아닌 응답은 기존의 낮은 confidence·재질문 분기로 처리합니다. 명확한 사이트 이용 표현의 기존 고정 안내 보정은 유지합니다. mock 모드에서 실제 클라이언트를 만들지 않는 것도 확인합니다.

## 안내원의 요청 범위 guard

기존 mock 분류기에 있던 추천·자격·당첨·실시간·내 조건·조건에 맞는 표현 검사를 실제 모드에서도 Provider 호출 전에 적용합니다. 정상 JSON으로 검증된 `TERM_EXPLANATION`도 금지 요청에 대한 답변이면 서비스 범위를 벗어납니다. 모의 Provider가 자격 판단 질문을 용어 설명으로 반환할 때 기존 코드에서 답변이 통과하는 것을 재현한 뒤, 동일 요청을 서버 규칙으로 거절하도록 보완했습니다. 규칙 거절은 `model=rule-guide`이며 Provider 생성·호출이 0회임을 검사합니다. 실제 지연·비용 절감액을 측정한 것은 아닙니다.

현재 질문에만 기존 표현 규칙을 적용합니다. 이전 대화의 금지 질문 때문에 새 사이트 사용법 질문을 막지 않습니다. 허용 용어 설명은 기존 Provider 경로를 유지합니다. 이 키워드 검사는 모든 바꿔 말하기·문맥 우회를 탐지하지 않으며, 모델 분류와 사람이 확인해야 하는 범위 한계를 그대로 둡니다.

안내원의 출력 계약도 `GuideClassification`을 그대로 강화합니다. 숫자 문자열·boolean confidence와 추가 필드는 거절하고, 용어·계산 category에는 공백 제거 후 비어 있지 않은 short_answer가 필요합니다. 구조적으로 정상이어도 빈 답변을 성공 answer로 반환하는 기존 동작을 재현했습니다. Provider에 같은 응답 스키마를 전달하고 JSON 반환 후 다시 검증합니다. 실패는 기존 confidence 0의 재질문 분기로 처리하며 명확한 사이트 사용법의 고정 보정은 유지합니다. 코드 블록 JSON 호환도 유지합니다. 모의 Provider로 검사했으며 실제 Gemini의 스키마 지원·답변 정확도를 평가한 것은 아닙니다.

## 상담 단계 추적

`workflow_trace.py`는 상담 요청마다 임의 UUID를 만들고 기록 조회, 모델 호출 또는 mock, 출력 검증, 저장, 기록 정리의 시작·완료·실패를 기존 `add_log`에 전달합니다. 요약 재시도 복구는 `summary.recover`로 구분합니다. 동일한 trace ID로 어떤 단계에서 실패했는지와 처리 시간을 연결할 수 있습니다. 질문·답변·사용자 ID·키·원본 예외 문구는 전달하지 않고 오류 유형은 허용된 고정 문자열만 사용합니다. 로그 장애가 원래 요청의 성공·실패를 바꾸지 않도록 합니다.

이 추적은 영구 감사 기록이 아닙니다. 기존 메모리 버퍼의 최근 200개 로그만 표시하며 서버 재시작으로 사라집니다. 단계마다 로그가 생기므로 이전보다 적은 수의 요청이 버퍼에 남습니다. error만 기존 DB 저장 큐를 사용하고 큐 포화·DB 장애 시 유실될 수 있습니다. 성공한 전체 실행 이력, 요청 취소, 모든 AI 기능의 추적은 보장하지 않습니다. API 응답과 DB 스키마는 유지합니다.

검증은 mock 상담의 단계 순서, 실제 로그 버퍼 연결, 동시 요청 ID 분리, 잘못된 출력·저장 실패에서 후속 단계 생략, 이미 저장된 요약 복구, 개인정보 제외, 로그 자체 장애의 영향 차단을 검사합니다. 실제 Gemini 품질·응답 시간 측정과 구분합니다.

### 화면 FAQ의 모델 호출 생략

화면에 표시한 사이트 사용법 질문 9개와 category 매핑을 housing_common.guide_faq에 공유합니다. 앞뒤 공백만 제거한 정확한 질문이 일치하면 기존 고정 안내를 rule-guide로 반환하고 Gemini 설정이나 호출이 필요하지 않습니다. 금지 표현 검사는 먼저 적용합니다. 용어 예시와 다른 표현은 기존 mock/Gemini 분류 경로를 유지합니다. 이는 일반적인 자연어 분류를 대체하지 않습니다. 테스트로 FAQ의 Provider 호출 0회와 용어 질문의 호출 1회를 확인했으며 실제 Gemini 비용·응답 시간은 측정하지 않았습니다.
