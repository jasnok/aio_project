# 공공임대 청약 안내 서비스 포트폴리오 리팩토링 계획

작성일: 2026-09-22. 현재 저장소와 회고 3편을 검토한 계획이며, 아래의 새 구조·설정·기능은 구현 예정이다. 이번 작업에서는 애플리케이션 코드와 실제 환경설정, 외부 데이터베이스를 변경하지 않았다.

## 1. 목표와 추천 방향

**기존 FastAPI·Streamlit·Supabase를 살리면서, 내 PC에서 재현 가능한 시연 환경을 먼저 만들고 무료 공개 체험판을 덧붙인다.** 공개 서비스가 잠들어 있어도 평가할 수 있도록 3~5분 시연영상과 기술 설명을 함께 준비한다.

리팩토링은 이미 지은 집의 배선과 배관을 정리하는 작업에 가깝다. 이미 잘 동작하는 공고 검색·이미지 관리·검증 기능은 보존하고, 설정·권한·저장 처리·화면 코드를 이해하고 수정하기 쉬운 구조로 바꾼다. 모든 파일을 검토하되, 모든 파일을 무조건 다시 작성하는 것을 목표로 삼지 않는다.

완성할 결과물은 다음 세 가지다.

1. **로컬 시연판:** 외부 유료 API 없이 공고 조회, 즐겨찾기, 관리자 등록·수정, 문서 처리 과정을 재현한다.
2. **무료 공개 체험판:** 방문자가 회원가입 없이 샘플 공고를 검색하고 핵심 흐름을 체험한다. 관리자 변경 작업은 서버에서 차단한다.
3. **취업 포트폴리오:** 실행 안내, 구조도, 실제 문제 해결 사례, 개선 전후 측정 결과, 영상, 본인 기여 범위를 설명한다.

우선 Streamlit을 유지한다. React 등으로 화면을 전면 교체하면 인증과 데이터 문제를 해결하기 전에 화면을 다시 만드는 일이 커진다. 지원 직무가 프런트엔드로 정해지면 사용자 화면 교체를 후속 범위로 검토한다. AI 오케스트레이션·백엔드 지원에서는 현재 기술만으로도 설계와 검증 역량을 보여줄 수 있다.

포트폴리오의 중심 설명은 **“긴 청약 공고를 검토 가능한 등록 초안으로 바꾸고, 사용자가 조건에 맞는 주택형을 비교하도록 돕는 서비스”**가 적합하다. 상담 챗봇·생활권 지도·로그는 이를 보조한다.

## 3. 현재 코드에서 확인한 사실

가상환경을 제외한 Python 파일은 BE 56개, FE_Admin 50개, FE_User 41개다. 단순 화면 변경보다 실행·인증·데이터·AI를 차례로 정리할 규모다.

| 발견 | 사용자가 겪을 수 있는 문제 | 근거 | 우선순위 |
|---|---|---|---|
| 관리자 변경·업로드 API에 인증 검사가 없음 | 관리자 화면에 들어가지 않고도 변경 요청을 보낼 수 있음 | `BE/app/routers/admin_router.py`, `BE/app/services/admin_service.py` | 공개 전 필수 |
| 프로필·즐겨찾기가 요청의 user_id를 신뢰함 | 다른 사용자의 정보나 즐겨찾기에 접근할 수 있음 | `BE/app/routers/profile_router.py`, `BE/app/routers/favorite_router.py` | 공개 전 필수 |
| 로그 조회 API도 권한 구분이 없음 | 운영 정보가 공개될 수 있음 | `BE/app/routers/log_router.py` | 공개 전 필수 |
| 서버 DB 연결에 service-role 사용 | 서버에서 권한을 검사하지 않으면 DB 정책만으로 막을 수 없음 | `BE/app/core/supabase_config.py` | 공개 전 필수 |
| 사용자·관리자 화면의 서버 주소 설정 방식이 다름 | 같은 설정을 넣어도 한쪽만 실행될 수 있음 | 양쪽 `core/api_client.py` | 높음 |
| Gemini 설정·호출이 BE와 관리자 화면에 나뉨 | 모델·오류·사용량 제한을 따로 관리해야 함 | `BE/app/core/gemini_config.py`, `FE_Admin/clients/gemini_client.py` | 높음 |
| mock 상담도 라우터에서 Redis 기록을 먼저 읽음 | AI 키가 없어도 Redis 미설정이면 상담을 이용하지 못함 | `BE/app/routers/chat_router.py`, `BE/app/services/chat_history_service.py` | 높음 |
| 사진 목록 교체가 삭제 후 삽입의 별도 DB 요청임 | 중간 실패 시 사진 관계가 일부만 변경될 수 있음 | `BE/app/services/listing_service.py`의 `listing_images_replace` | 높음 |
| 수동 SQL 파일들이 여러 단계의 변경을 담음 | 새 DB를 만드는 순서가 모호하고 현재 상태를 재현하기 어려움 | `BE/sql/` | 높음 |
| 저장소 SQL에 상담 요약 테이블·권한 정책의 완전한 재현 절차가 없음 | 기존 클라우드에서는 되던 기능이 새 환경에서 실패할 수 있음 | `BE/sql/`, `BE/app/services/chat_service.py` | 높음 |
| 관리자 관리 화면 757줄, 자동 등록 화면 401줄 | 한 기능을 고칠 때 다른 화면 상태를 깨뜨리기 쉬움 | `FE_Admin/app_pages/03_listing_manage.py`, `08_listing_auto_create.py` | 중간 |
| 면적·지역 상수 등 일부 코드가 두 FE에 중복됨 | 한쪽만 수정되어 표시·규칙이 달라질 수 있음 | 양쪽 `core/area_format.py`, `core/constants.py` | 중간 |
| 전체 조회·검색과 페이지 조회의 동작이 나뉨 | 데이터가 늘면 응답량과 정렬·마감 처리의 차이가 커짐 | `BE/app/services/listing_service.py` | 중간 |
| README는 AI 미포함, 기존 계획서는 모의 로그 설명 | 실제 기능과 설명이 달라 평가자가 혼란스러움 | `README.md`, `docs/plan.md`, `BE/app/main.py` | 높음 |

중요한 구분: 관리자 화면을 숨기는 것과 관리자 API를 보호하는 것은 다르다. 화면은 출입문이고 API는 실제 작업을 수행하는 창구다. 창구에서도 신분과 권한을 확인해야 한다. CORS 설정도 인증을 대신하지 않는다.

현재 테스트는 BE **172개**, 관리자 **331개**, 사용자 **156개**, 합계 **659개**가 통과했다. 기존 각 폴더의 가상환경에서 unittest를 실행했고 외부 네트워크 연결을 차단했다. 따라서 이는 기존 자동 테스트의 결과이며, 실제 Supabase·Gemini·Redis 연결이나 브라우저 전체 동작이 검증되었다는 뜻은 아니다. 일부 오류 경로에서 로그 저장을 위해 외부 DB 연결을 시도하므로 테스트와 로그 저장의 분리도 필요하다.

실제 .env는 값 대신 설정 이름과 존재 여부만 점검했다. 기존 키의 유효성, 클라우드 DB의 실제 내용·RLS 설정, Git 전체 이력의 비밀 유출 여부는 아직 검증하지 않았다.

## 4. 실행 환경 설계

### A. 로컬 시연판 — 먼저 완성

| 구성 | 사용할 방식 | 이유 |
|---|---|---|
| 사용자·관리자 화면 | 기존 Streamlit | 이미 만든 기능을 활용 |
| API 서버 | 기존 FastAPI | 두 화면이 공통 규칙 사용 |
| DB·회원 인증·파일 | Supabase CLI + 로컬 Docker 실행 환경 | 기존 Auth·Storage 구조를 크게 바꾸지 않고 재현 |
| 진행 중 대화 | 용량·시간 제한이 있는 메모리 저장 기본, 로컬 Redis 선택 | Redis 설치를 기본 기능의 필수 조건에서 제외 |
| 보존할 상담 요약 | 로컬 Supabase DB | 재시작 후에도 보관할 데이터와 임시 데이터를 구분 |
| AI | 샘플 재생 기본, Gemini 무료 범위 또는 Ollama 선택 | 키가 없어도 화면 흐름을 시연 |
| 지도·주변 시설 | 샘플 좌표·시설 목록 기본, Kakao 연결 선택 | 지도 키 없이도 위치 정보를 확인 |

Supabase는 일반 DB뿐 아니라 로그인과 파일 저장에도 사용한다. 따라서 URL만 SQLite로 바꾸는 방식은 성립하지 않는다. 로컬 Supabase 유지가 우선이며, PC 자원이 부족할 때만 Supabase Free 연결을 현실적인 대안으로 쓴다. 이 대안은 무료일 수 있어도 완전한 오프라인 실행은 아니다.

로컬 Supabase는 Docker 호환 환경이 필요하며 PC 메모리와 디스크 여유를 먼저 확인한다. 최초 패키지·이미지·모델 다운로드에는 인터넷이 필요하다. 설치 후 외부 API를 끈 시연이 가능한지 별도로 검증한다. 로컬 개발 스택은 외부 공개용으로 노출하지 않는다. [Supabase 로컬 실행 안내](https://supabase.com/docs/guides/local-development/cli-workflows)

지도 배경도 현재 CARTO 외부 주소를 사용하므로 Kakao 키를 없애는 것만으로 오프라인 지도가 되지는 않는다. 기본 대체 화면은 주소·좌표·거리 목록으로 만들고, 완전 오프라인 지도가 필요할 때만 별도 범위를 잡는다.

### B. 무료 공개 체험판 — 권한 보완 후

추천 구성은 **사용자 화면: Streamlit Community Cloud / API: Render Free 1개 / DB·Auth·Storage: Supabase Free**다. 무료 제공 주소를 사용하고 유료 도메인은 필수로 두지 않는다. 관리자 전체 작업은 우선 로컬에서 시연한다.

| 서비스 | 계획에 반영할 무료 조건 |
|---|---|
| Render Free | 15분 무요청 시 휴면, 복귀 약 1분. 월 750시간은 워크스페이스 공유. 로컬 파일은 재시작·배포·휴면 시 사라지므로 DB·업로드를 보관하지 않음. 전송량·빌드 초과와 결제수단 설정에 따라 청구 또는 중단 가능. [공식 문서](https://render.com/docs/free) |
| Streamlit Community Cloud | 무료 제공, 12시간 무트래픽이면 휴면. 방문자용 시작 안내와 영상 링크 필요. [공식 관리 안내](https://docs.streamlit.io/deploy/streamlit-community-cloud/manage-your-app) |
| Supabase Free | DB 500MB, 파일 1GB 등의 한도와 비활성 프로젝트 휴면 정책이 있음. 작은 샘플·압축 이미지 사용. [가격표](https://supabase.com/pricing) |
| Supabase 기본 이메일 | 일반 방문자 대상 가입 메일에 제한이 있으므로 기본 발송만으로 공개 회원가입을 완성했다고 가정하지 않음. [SMTP 안내](https://supabase.com/docs/guides/auth/auth-smtp) |
| Gemini | 일부 모델의 무료 범위가 있지만 계정·모델별 호출 제한을 확인해야 함. 무료 호출을 필수 동작 조건으로 두지 않음. [가격표](https://ai.google.dev/gemini-api/docs/pricing), [한도](https://ai.google.dev/gemini-api/docs/rate-limits) |

조건은 2026-09-22 확인 기준이며 실제 배포 직전에 다시 확인한다. 운영비 0원을 우선하면 한도 도달 시 기능을 멈추거나 샘플로 전환하고, 유료 API로 자동 전환하지 않는다. 공개 무료 호스팅에서 로컬 대형 AI 모델을 직접 실행하는 구성은 기본안에서 제외한다.

공개 범위는 다음과 같이 제한한다.

- 회원가입 없이 샘플 공고 검색·상세 확인·원문 링크 이동.
- 즐겨찾기 체험은 방문자별 화면 세션에 보관하고 저장 범위를 안내. 실제 계정의 영구 즐겨찾기는 인증 기능 검증 후 제공.
- AI는 예시 질문과 샘플 결과 체험을 기본 제공. 실제 AI 활성화 시 사용자별·전체 요청량 상한과 입력 길이 제한 적용.
- 문서 자동 등록은 샘플 문서의 추출·수정 미리보기까지만 공개. 공용 데이터 변경·임의 대용량 업로드는 서버에서도 막음.
- 모든 방문자가 같은 관리자 계정이나 같은 대화 기록을 공유하지 않음.
- 실제 회원가입 공개는 OAuth 또는 별도 이메일 발송 구성을 검증하는 후속 단계로 분리.

### C. .env와 URL 정리 규칙

.env는 접속 주소와 비밀키를 모아 둔 설정표다. 파일 자체가 비용을 발생시키는 것이 아니라, 연결한 서비스와 사용하는 기능이 비용에 영향을 준다.

1. 로컬 / 공개 데모 실행 모드를 명시한다. 아래 이름은 새 설계 예시이며 현재 지원 설정이 아니다.
2. `APP_MODE=local|public_demo`, `AI_PROVIDER=sample|gemini|ollama`, `CHAT_STORE=memory|redis`, `LOCATION_PROVIDER=sample|kakao`처럼 목적을 분리한다.
3. 환경변수·Streamlit secrets·로컬 .env의 우선순위를 문서와 코드에서 통일한다. 실제 키는 출력하지 않는다.
4. 서버에는 강한 DB 키, 화면에는 필요한 공개 설정만 전달한다. 관리자 인증 정보는 서버에서 검증한다.
5. 필수 설정 누락은 시작할 때 읽기 쉬운 메시지로 표시한다. 선택 기능의 키 누락은 해당 기능만 비활성화한다.
6. `.env.example`과 secrets 예시를 완성하고, 누락된 관리자 설정 예시를 추가한다.
7. API 접속 URL은 설정으로, 파일 참조는 가능한 한 저장소 경로로 관리한다. 공고 원문 링크는 환경 URL이 아니라 콘텐츠이므로 유지한다.
8. 실제 키가 Git 이력에 들어간 사실이 확인되면 해당 키를 교체한다. 현재 노출이 확인되었다는 의미는 아니다.

## 5. 전체 코드 리팩토링 범위

| 영역 | 작업 | 완료 기준 |
|---|---|---|
| 설정·실행 | 설정 읽기 통합, 버전 정리, 설치·실행·종료 스크립트, 상태 확인 API | 새 환경에서 문서만 보고 실행 |
| 인증·권한 | 사용자 토큰 검증 재사용, 관리자 역할 서버 확인, 본인 정보만 처리 | 비로그인 401, 일반 사용자 관리자 작업 403, 타인 정보 접근 차단 |
| DB·SQL | 순서가 있는 마이그레이션, 샘플 데이터, Auth 트리거·Storage·RLS·요약 테이블 재현 | 빈 로컬 DB에서 전체 기능 준비 가능 |
| 공고·즐겨찾기·프로필 | 저장 접근과 업무 규칙 분리, 검증 통일, 검색·정렬·페이지 계약 통합 | 같은 조건에서 사용자·관리자 결과 일치 |
| 이미지 | DB 변경을 한 묶음으로 처리, 파일 정리 재시도, 공유 파일 보호, 업로드 제한 | 중간 실패에도 기존 공고·사진 관계 보존 |
| 관리자 화면 | 검색·목록·편집·사진·삭제 영역 분리, 자동 등록 단계 분리 | 화면 상태 변경이 다른 영역을 깨뜨리지 않음 |
| 사용자 화면 | 공개 체험 진입, 카드·필터 정리, 빈 결과·휴면·오류·토큰 만료 안내 | 처음 온 방문자가 핵심 기능까지 쉽게 도달 |
| 공통 FE | 면적·금액·날짜·지역·카드·API 오류 등 실제 중복만 공유 | 규칙 수정이 두 화면에 일관되게 반영 |
| AI | 문서 처리·추출·검증·등록 단계와 제공자 호출 분리 | 샘플/실제 AI를 교체해도 동일한 검증 사용 |
| 지도 | Kakao 중복 함수 정리, 미완성 helper 확인, 키 없는 대체 화면 | 지도 장애가 공고 조회를 막지 않음 |
| 대화·요약 | 임시 저장과 영구 저장 구분, 만료·용량·사용자 격리 | Redis 없이 기본 시연, 사용자간 기록 비공유 |
| 로그·예외 | 민감정보 제거, 요청 추적, 동기 DB 로그 저장이 응답을 지연시키지 않게 개선 | 장애 시 사용자 안내와 운영 원인 추적 가능 |
| 테스트·문서 | 기존 테스트 유지, 중요한 통합 경로 보강, 자동 검사와 실제 상태 문서화 | 변경 시 재발 여부를 자동 확인 |

DB 변경을 한 묶음으로 처리한다는 것은 “공고 수정과 사진 목록 수정이 둘 다 성공하거나 둘 다 취소되게 한다”는 뜻이다. Storage 파일은 DB 트랜잭션에 자동으로 포함되지 않으므로, DB 확정 후 파일 정리와 실패 재시도를 별도로 설계한다. 기존의 ‘참조 확인 실패 시 삭제하지 않기’ 원칙은 유지한다.

권한은 가능하면 사용자·관리자 모두 Supabase Auth로 통일하고, 관리자 역할은 사용자가 직접 바꿀 수 없는 서버 관리 정보로 둔다. 기존 admins 계정을 어떻게 옮길지 결정한 뒤 전환한다. 사용자 정보는 요청에 적힌 user_id 대신 검증한 로그인 정보에서 가져온다. DB 정책은 별도 보호층이며 service-role을 쓰는 서버 검증을 대신하지 않는다.

폴더는 처음부터 전부 옮기지 않는다. BE/FE_Admin/FE_User 위치를 유지한 채 기능 단위로 분리하고, 테스트가 통과하는 작은 변경으로 진행한다. 공통 모듈은 두 FE에서 설치 가능한 패키지로 두어 배포 시 import 경로가 우연히 맞는 구조를 피한다.

## 6. AI 기능의 완성 기준

가장 먼저 다듬을 AI 기능은 공고 자동 입력이다. 본인 기여가 분명하고, 문서 처리 → AI 해석 → 검증 → 사람 확인 → 등록이라는 흐름을 설명하기 좋다.

1. PDF/HWPX 업로드 크기·쪽수·압축 해제 크기·이미지 개수를 제한한다.
2. 문서에서 텍스트·이미지를 꺼내는 작업은 일반 코드로 처리한다.
3. AI 제공자는 정해진 입력·출력 형태로 호출한다. PDF 원본 이해와 일반 텍스트 추출은 같은 성능이라고 가정하지 않는다.
4. 숫자·날짜·지역·필수값과 공고-이미지 연결을 검증한다.
5. 원문 쪽 번호 또는 근거 문구를 함께 보여주고 관리자가 수정·선택한다.
6. 같은 등록을 다시 눌러도 중복 생성되지 않도록 작업 식별자와 문서·항목 기준 중복 검사를 둔다.
7. 일부 등록 실패 시 성공 항목은 유지하고 실패 항목만 재시도한다. 임시 업로드의 사용 여부를 확인해 정리한다.

샘플 모드는 ‘이 샘플 문서의 저장된 분석 결과’라고 명시한다. 임의 문서를 실제로 분석한 것처럼 보여주지 않는다. Ollama는 선택 확장이며, PC 성능과 모델의 문서·이미지 이해 능력을 별도로 검증한다. 우선 텍스트 기반 상담 또는 추출부터 비교하고 Gemini의 PDF·이미지 기능을 곧바로 대체한다고 약속하지 않는다. [Ollama FAQ](https://docs.ollama.com/faq)

상담은 저장된 공고의 내용과 원문 링크를 근거로 안내하는 방향을 우선한다. 청약 자격 확정은 하지 않고 문서에 없는 내용은 모른다고 답하도록 검증한다. 초기부터 벡터 DB·다중 에이전트·복잡한 워크플로 도구를 추가할 필요는 없다. 소규모 공고 검색과 검증으로 해결되는지 먼저 측정한다.

무료 Gemini 입력은 제품 개선에 사용될 수 있으므로 공개 체험에는 가상의 사용자 정보와 샘플 문서를 사용한다. [Gemini 약관](https://ai.google.dev/gemini-api/terms)

평가 자료는 대표 PDF/HWPX 5~10개에서 시작한다. 주택형별 보증금·월세·면적·날짜의 정답, 이미지 연결 정답을 마련해 필드 정확도, 사람 수정 개수, 처리 시간, 실패율, 호출량을 기록한다. 개선 수치는 측정 후에만 포트폴리오에 쓴다.

## 7. 권장 순서와 예상 작업량

1인 기준의 계획 추정치이며 PC 환경·라이브 DB 상태에 따라 달라진다. 약 62~96시간, 주 15시간이면 대략 5~7주를 예상한다. 학습 시간은 추가될 수 있다.

| 단계 | 예상 | 구체 작업 | 통과 기준 |
|---|---:|---|---|
| 0. 기준선 보존 | 4~6시간 | 현재 버전·핵심 화면·테스트 기록, 팀/개인 기여 분리, 외부 연결 목록 | 무엇이 원래 되던 기능인지 확인 가능 |
| 1. 로컬 실행 | 12~18시간 | 설정 통일, 로컬 Supabase, 마이그레이션·샘플·실행 스크립트, Redis 선택화 | 클라우드 키 없이 기본 여정 시연 |
| 2. 인증·데이터 보호 | 10~16시간 | 관리자 역할, 본인 데이터 검사, DB 정책, 이미지 변경 실패 처리 | 권한 우회·중간 실패 시나리오 통과 |
| 3. 구조·화면 정리 | 16~24시간 | 큰 페이지 분리, 공통 모듈, 검색·페이지 API 통일, 오류·로그 정리 | 기존 회귀 테스트와 브라우저 주요 여정 통과 |
| 4. AI 품질·재현성 | 12~20시간 | 샘플/실제 AI 경로, 추출 평가, 근거 표시, 중복 방지·재시도 | 정답 자료와 측정표로 품질 설명 가능 |
| 5. 공개·포트폴리오 | 8~12시간 | 무료 제한 데모, 휴면 안내, README·구조도·영상·면접 설명 | 다른 사람이 링크 또는 영상으로 핵심 가치 확인 |

첫 번째 완료 지점은 1단계의 로컬 시연이다. 무료 공개 배포 조건이 맞지 않아도 최종 결과를 로컬 실행판·영상·측정 자료로 완성할 수 있다. 공개 배포는 2단계의 권한 검증을 통과한 뒤에 진행한다.

새 기능을 한꺼번에 섞지 않고 설정 → 권한 → 이미지 저장 → 화면 → AI처럼 작은 변경 묶음으로 진행한다. 기존 데이터가 있는 DB와 개발용 초기화 명령을 분리하고, 원격 DB 초기화를 기본 실행 절차에 넣지 않는다.

## 8. 검증과 포트폴리오 증거

기존 659개 테스트를 기반으로 중요한 빈틈을 보강한다. 테스트 개수를 늘리는 것보다 실제 오류를 막는지가 기준이다.

- 비로그인·일반 사용자·관리자·다른 사용자의 권한 경계를 검사한다.
- 실제 프런트엔드가 만든 이미지 요청을 API까지 보내고 남은 사진을 확인한다.
- DB 수정 실패·일부 업로드 실패·같은 이미지 공유·동시 수정 시 기존 데이터를 보존한다.
- 1,000건의 샘플에서도 필터·정렬·마감 공고 처리·페이지 이동에 중복이나 누락이 없는지 확인한다.
- AI 키 없음·호출 한도 초과·잘못된 응답·Redis 장애·지도 장애에도 핵심 조회가 동작하는지 확인한다.
- 두 브라우저의 로그인·즐겨찾기·대화가 섞이지 않는지 확인한다.
- 새 로컬 DB에서 설치 → 초기 데이터 → 실행 → 재시작을 재현한다.
- 공개 환경은 첫 접속과 휴면 복귀, 이미지 영구 보관, 관리자 요청 차단을 확인한다.

성능은 같은 데이터·환경·요청 조건에서 평균뿐 아니라 p95 응답시간과 오류율을 측정한다. 기존 회고의 수치를 이번 개선 결과로 재사용하지 않는다. 외부 연결 없는 테스트 결과와 실제 통합 검증 결과도 구분한다.

샘플 데이터는 실제 개인정보가 없는 가상 공고를 기본으로 한다. 과거 실제 공고를 사용하는 경우 원래 날짜와 출처를 유지하고, 모집 중인 실제 공고처럼 날짜를 바꾸지 않는다. 가상 공고에는 시연용 표기를 하고 신청 전/모집 중/마감 상태를 고정된 기준일로 재현할 수 있게 한다.

## 9. 취업용 결과물과 영상 구성

권장 소개 문장: **“공공임대 공고를 검색·비교하고, AI 문서 분석 결과를 관리자 검토를 거쳐 등록하는 Python 기반 안내 서비스.”**

README 첫 화면에는 서비스가 해결하는 문제, 대표 화면, 체험 링크·영상, 로컬 실행 안내, 본인 기여를 배치한다. 상세 문서에는 구조와 데이터 흐름, 선택 이유, 실패 처리, 검증 결과와 남은 한계를 둔다.

세 가지 문제 해결 사례를 중심으로 설명한다.

1. **이미지 삭제 안전성:** 잘못된 요청으로 전체 삭제가 발생했던 원인 → 요청 검증 → DB와 파일의 실패 처리 → 재발 방지 테스트.
2. **AI 문서 입력:** 문서 형식별 전처리 → 구조화 → 값 검증 → 관리자 수정 → 중복 없는 저장 → 정확도·작업 시간 측정.
3. **실행 재현성과 공개 준비:** 개인 환경 의존 → 설정·DB 준비 자동화 → 권한 검사 → 무료 제한 데모와 장애 대체 흐름.

3~5분 영상 예시:

| 시간 | 보여줄 내용 |
|---|---|
| 0:00~0:30 | 어떤 문제를 해결하는지와 샘플 환경 표시 |
| 0:30~1:30 | 공고 필터·정렬·상세·즐겨찾기 |
| 1:30~3:00 | 문서 업로드·추출 결과·잘못 읽힌 값 수정·관리자 등록 |
| 3:00~4:00 | 사진 일부 삭제 후 다른 사진 보존, 실패 상황 안내 |
| 4:00~5:00 | 전체 구조, 본인 개선, 실제 측정 결과 |

실제 AI 실행과 샘플 재생은 영상에서도 구분한다. 회원정보·키·로그인 토큰은 촬영 화면에서 제외한다. 팀 프로젝트 전체를 개인 단독 개발로 소개하지 않고, 원래 팀 기여와 개인 리팩토링 결과를 나눠 보여준다.

## 10. 다음 구현 작업의 시작점

첫 변경 묶음은 **실행 설정 통일 + 로컬 DB 재현 + 샘플 데이터 + 실행 안내**로 한다. 이후 인증과 이미지 저장을 보완하고 화면·AI 정리를 이어간다. 현재 소스와 문서에서 드러난 상태를 기준으로 한 계획이므로, 첫 구현 단계에서 PC 자원과 실제 DB 스키마 차이를 확인해 세부 작업량을 조정한다.
