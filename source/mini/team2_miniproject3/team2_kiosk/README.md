# 햄버거 음성 키오스크 RAG 데이터 설계 가이드

햄버거 음성 키오스크 프로젝트에서 RAG는 단순히 메뉴 정보를 긴 문장으로 저장하는 것보다, **검색용 자연어 설명 + 구조화된 메타데이터**를 함께 저장하는 방식이 가장 관리하기 좋습니다.

사용자는 예를 들어 아래처럼 말할 수 있습니다.

- "매운 버거 추천해줘"
- "치즈 들어간 거 뭐 있어?"
- "새우 들어간 메뉴 중에 세트로 먹을 만한 거 알려줘"
- "10,000원 안쪽으로 추천해줘"

이런 질문에 대응하려면 메뉴 데이터를 구조화해서 저장하고, 자연어 검색에 필요한 내용은 임베딩용 텍스트로 별도 관리하는 것이 좋습니다.

---

## 1. 메뉴 데이터 JSON 예시

```json
{
  "id": "burger_001",
  "category": "burger",
  "name": "불고기 버거",
  "price": 6500,
  "description": "달콤한 불고기 소스와 소고기 패티가 들어간 버거입니다.",
  "ingredients": [
    "소고기 패티",
    "양상추",
    "양파",
    "불고기 소스"
  ],
  "spicy": false,
  "allergy": [
    "밀",
    "대두"
  ],
  "available": true
}
```

이처럼 가격, 재료, 매운맛 여부, 알레르기 정보, 판매 가능 여부는 구조화된 필드로 분리해 두는 것이 좋습니다.

---

## 2. RAG용 자연어 텍스트 예시

벡터 검색에는 JSON 전체를 그대로 임베딩하기보다, 검색에 사용할 자연어 문장을 따로 만드는 것을 추천합니다.

```text
메뉴명: 불고기 버거

카테고리: 햄버거

가격: 6,500원

설명:
달콤한 불고기 소스를 사용한 소고기 패티 햄버거입니다.
매운맛이 없어서 매운 음식을 좋아하지 않는 고객에게 적합합니다.

주요 재료:
소고기 패티, 양상추, 양파, 불고기 소스

알레르기 정보:
밀, 대두

추천:
달콤한 맛의 버거를 원하는 고객,
맵지 않은 햄버거를 원하는 고객에게 추천합니다.
```

이 텍스트를 임베딩해서 pgvector에 저장하면 의미 기반 검색이 가능합니다.

---

## 3. PostgreSQL + pgvector 테이블 예시

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE menu_items (
    id SERIAL PRIMARY KEY,

    menu_code VARCHAR(50) UNIQUE NOT NULL,
    name VARCHAR(100) NOT NULL,
    category VARCHAR(50),

    price INTEGER,

    description TEXT,
    ingredients TEXT[],

    spicy BOOLEAN DEFAULT FALSE,
    allergy TEXT[],

    available BOOLEAN DEFAULT TRUE,

    rag_text TEXT,

    embedding VECTOR(768)
);
```

핵심 필드는 다음과 같습니다.

- `price`: 가격 필터링
- `ingredients`: 재료 기반 조건 검색
- `spicy`: 매운맛 여부
- `available`: 현재 판매 가능 여부
- `rag_text`: 자연어 기반 검색에 사용할 텍스트
- `embedding`: 임베딩 벡터 저장

## 7. 벡터 검색 예시

사용자가 음성으로 아래처럼 말한다고 가정합니다.

```text
"매운 햄버거 먹고 싶어."
```

STT 결과:

```python
user_query = "매운 햄버거 먹고 싶어"
```

이 문장을 임베딩한 뒤 pgvector에서 유사도를 검색합니다.

```sql
SELECT
    name,
    price,
    rag_text
FROM menu_items
ORDER BY embedding <=> %(query_embedding)s
LIMIT 3;
```

예상 결과:

```text
1. 핫치킨 버거
2. 더블치즈 버거
3. 불고기 버거
```

검색 결과를 LLM에 Context로 전달합니다.

```text
사용자 질문:
매운 햄버거 먹고 싶어.

검색된 메뉴 정보:

[메뉴 1]
핫치킨 버거
가격: 7,000원
매콤한 치킨 패티 햄버거.
매운맛을 좋아하는 고객에게 추천.

[메뉴 2]
더블치즈 버거
가격: 8,500원
소고기 패티 두 장과 치즈가 들어간 메뉴.
매운맛 없음.

사용자의 요구에 가장 맞는 메뉴를 추천하세요.
메뉴 데이터에 없는 정보는 만들어내지 마세요.
```

LLM 응답 예시:

```text
매운 메뉴를 원하시면 핫치킨 버거를 추천드려요.
가격은 7,000원이고 바삭한 치킨 패티와 매운 소스가 들어가요.
주문하시겠어요?
```

## 8. 가격 같은 조건은 SQL로 검색하기

사용자가 다음과 같이 말할 수 있습니다.

```text
"8천 원 이하 햄버거 보여줘."
```

이 경우는 벡터 검색보다 SQL이 더 정확합니다.

```sql
SELECT *
FROM menu_items
WHERE price <= 8000
AND available = TRUE;
```

예상 결과:

```text
불고기 버거 6,500원
핫치킨 버거 7,000원
새우 버거 7,500원
```

## 9. 재료 조건 검색 예시

사용자가 다음과 같이 말한다고 가정합니다.

```text
"치즈 안 들어가는 버거 보여줘."
```

예시 SQL:

```sql
SELECT *
FROM menu_items
WHERE NOT ('치즈' = ANY(ingredients));
```

실제 프로젝트에서는 `체다치즈`, `모짜렐라치즈`처럼 재료명이 다양할 수 있으므로 재료 표준화 또는 별도 재료 테이블을 사용하는 방법도 고려할 수 있습니다.

## 10. 추천 구조: Hybrid RAG

키오스크에서는 RAG만 사용하는 것보다 **SQL 조건 검색 + pgvector 의미 검색**을 함께 사용하는 Hybrid RAG 구조가 좋습니다.

```text
                 🎤 사용자 음성
                       │
                       ▼
                     STT
                       │
                       ▼
               "만원 이하에서
                안 매운 거 추천해줘"
                       │
                       ▼
                     LLM
                의도 / 조건 추출
                       │
              ┌────────┴────────┐
              ▼                 ▼
         PostgreSQL          pgvector
        정확한 조건 검색     의미 기반 검색
              │                 │
              │                 │
         price <= 10000     "안 매운 메뉴"
         available=true     "담백한 메뉴"
              │                 │
              └────────┬────────┘
                       ▼
                검색 결과 통합
                       │
                       ▼
                     LLM
                       │
                       ▼
        "새우 버거를 추천드립니다."
                       │
                ┌──────┴───────┐
                ▼              ▼
               TTS           화면 표시
```

## 11. 추천 DB 구성

메뉴만 저장하지 말고 처음부터 카테고리를 나눠두면 확장하기 쉽습니다.

```text
menu_items
├─ 햄버거
├─ 사이드
├─ 음료
└─ 디저트

set_menus
├─ 불고기 버거 세트
├─ 핫치킨 버거 세트
└─ 새우 버거 세트

├─ 치즈 추가 +500
├─ 패티 추가 +1500
├─ 감자튀김 → 치즈스틱 +1000
└─ 음료 사이즈업 +500

faq
├─ 포장 가능 여부
├─ 결제 방법
├─ 영업시간
└─ 알레르기 안내
```

## 12. 중요한 설계 원칙

가격, 재고, 옵션처럼 정확한 값은 RAG 문장에만 저장하지 말고 반드시 DB 컬럼에도 저장하는 것이 좋습니다.

좋지 않은 예:

```text
불고기 버거는 6500원입니다.
```

이 문장만 RAG에 저장하면 가격 비교나 정렬 같은 조건 검색이 어려워집니다.

권장 방식:

```text
DB
name = 불고기 버거
price = 6500
available = true
```

그리고 RAG에는 의미 기반 검색에 유리한 내용을 저장합니다.

```text
불고기 버거는 달콤한 불고기 소스가 특징이며
맵지 않은 메뉴를 원하는 고객에게 추천합니다.
```

즉, 역할을 다음과 같이 나누는 것이 좋습니다.

- **DB**: 가격, 재고, 옵션, 판매 여부 등 정확한 데이터
- **RAG**: 맛, 특징, 추천 상황, 자연어 설명 등 의미 기반 데이터

## 13. 추천 구현 순서

PostgreSQL + pgvector + Ollama 구조라면 아래 순서로 진행하는 것이 좋습니다.

1. `menu_items` 테이블 생성
2. 햄버거 샘플 데이터 10~15개 작성
3. 각 메뉴의 `rag_text` 생성
4. Ollama 임베딩 모델로 `rag_text` 임베딩
5. pgvector에 임베딩 저장
6. 사용자 질문을 임베딩
7. pgvector 유사도 검색
8. 가격·매운맛·재고 등은 SQL 조건 검색
9. SQL 결과와 RAG 결과 통합
10. LLM에 Context 전달
11. 최종 추천 문장 생성
12. TTS로 음성 출력

## 14. 전체 프로젝트 흐름 예시

```text
사용자 음성
   ↓
STT
   ↓
사용자 문장
   ↓
LLM 의도 분석
   ↓
조건 추출
   ├─ 가격
   ├─ 매운맛
   ├─ 재료
   └─ 메뉴 취향
   ↓
PostgreSQL + pgvector 검색
   ↓
검색 결과
   ↓
LLM 답변 생성
   ↓
화면 출력 + TTS
```

이 구조로 구현하면 단순한 챗봇이 아니라 **자연어로 메뉴를 검색하고 추천하며 주문까지 이어지는 AI 음성 키오스크**로 발전시킬 수 있습니다.
