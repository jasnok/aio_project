지금 구조(병렬 조사 → 검증·취합 → 핸드오프 → 작성·요약)를 그대로 유지하면서 폭염·한파 알리미에 맞게 바꾸면 이렇게 됩니다.

## 1. 전체 구조

```
                         START

                           ▼

                           │

            Weather     Shelter     Profile

                │          │          │

                           ▼
                       Validation
                           │
                       Join Guard
                           │

                           │

                           │

                           │
```

## 2. 에이전트별 역할

**Weather Agent**
- 데이터: 기상청 단기예보(기온, 습도, 풍속), 기상청 기상특보
- 입력: 거주지 좌표(격자 nx, ny로 변환 필요)
- 출력: 오늘·내일 최고/최저기온, 체감온도, 특보 종류(폭염주의보/경보, 한파주의보/경보)

**Shelter Agent**
- 데이터: 행정안전부 무더위쉼터, 한파쉼터
- 입력: 거주지 좌표, 계절
- 출력: 가까운 쉼터 3곳(이름, 주소, 거리, 운영시간, 야간·휴일 개방 여부)
- 계절에 따라 어느 데이터를 쓸지 이 에이전트가 고릅니다.

**Profile Agent**
- 데이터: 사용자 입력(공공데이터 아님)
- 입력: 나이, 혼자 사는지, 지병(고혈압, 심장질환, 당뇨 등), 거동 가능 여부, 에어컨·난방 유무
- 출력: 취약 요인 목록과 취약도(상/중/하)
- 예시의 Health Agent 자리인데, **진단은 하지 않고 "주의가 필요한 요인"만 정리**하도록 프롬프트에 제한을 두세요.

## 3. Guard와 Validation에서 체크할 것

**Validation** (각 에이전트 결과를 개별 검사)
- 기온 값이 범위 안에 있는가(예: -40~50℃)
- 쉼터가 0곳이면 검색 반경을 넓혀 재시도
- 쉼터 운영시간이 현재 시각과 맞는가

**Join Guard** (3개 결과가 다 모였는가)
- 하나라도 실패하면? 정책을 미리 정해야 합니다. 예를 들어 Weather가 실패하면 중단, Shelter가 실패하면 "쉼터 정보 없음"으로 진행

**Handoff Guard** (Orchestration 2로 넘길 가치가 있는가)
- 특보 없음 + 체감온도 정상 + 취약도 하 → 알림 없이 종료
- 이 분기가 있어야 "매일 쓸데없는 알림"을 막을 수 있고, 멀티에이전트에서 Guard를 쓰는 이유가 잘 드러납니다.

## 4. 결과 스키마 예시

```json
// SafetyResearchResult
{
  "weather": { "max_temp": 35.2, "feels_like": 37.0, "warning": "폭염경보" },
  "shelters": [{ "name": "○○경로당", "distance_m": 320, "open": "09:00-18:00" }],
  "profile": { "age": 78, "lives_alone": true, "risk_factors": ["고혈압"], "vulnerability": "상" }
}

// AlertResult
{
  "risk_level": "위험",
  "actions": ["오후 2~5시 외출 자제", "물 자주 마시기"],
  "recommended_shelter": "○○경로당",
  "notify_guardian": true
}
```

## 5. Orchestration 2 설계 포인트

**Writer Agent**
- 위험도를 관심/주의/경고/위험 4단계로 판정합니다. 특보 등급 + 취약도를 조합하는 규칙표를 프롬프트에 넣으세요. (예: 폭염주의보 + 취약도 상 → 경고)
- 판정 근거를 함께 출력하게 하면 디버깅이 쉬워집니다.

**Summary Agent**
- **어르신용**: 문자 한 통 분량(90자 안팎), 쉬운 말, 숫자는 최소화, 행동 하나만 강조
- **보호자용**: 위험도, 근거, 추천 쉼터, "전화 한 통 드려보세요" 같은 권고
- 같은 정보를 대상별로 다르게 쓰는 게 이 에이전트의 존재 이유예요.

## 6. 개발 순서 추천

1. Weather Agent만 단독으로 만들어 API 호출 확인 (격자 변환이 첫 난관입니다)
2. Shelter Agent 추가 후 병렬 실행 + Join Guard
3. Profile Agent는 처음엔 하드코딩한 테스트 프로필 3~4개로 시작
4. Handoff Guard로 "알림 보낼 날 / 안 보낼 날" 분기 테스트
5. 마지막에 Writer, Summary 붙이기

테스트 시나리오는 "한여름 혼자 사는 80대 고혈압 어르신", "한겨울 가족과 사는 70대", "날씨 정상인 날" 정도로 잡으면 Guard 분기가 모두 검증됩니다.

특보 발령 기준(폭염은 체감온도, 한파는 아침 최저기온 기준)은 기상청 사이트에서 최신 기준을 확인해서 Writer의 규칙표에 넣으세요. 원하시면 다음으로 각 에이전트의 시스템 프롬프트를 작성해 드릴게요.

## 결론부터 말하면, 구조 자체는 괜찮은데 프로젝트 주제와 한 군데 크게 어긋나 있어요. 3차 가이드의 주제는 "에러 자가 치유(AutoHealing)"인데, 초안은 "폭염·한파 알리미 기능"만 설계되어 있고 장애가 났을 때 어떻게 복구하는지가 빠져 있습니다. 이게 유일하게 꼭 고쳐야 할 부분이고, 나머지는 작은 보완이에요.

꼭 고쳐야 할 것: 장애 복구 흐름 추가

가이드 평가의 중심이 "감지 → 판단 → 복구"라서, 지금 초안 그대로면 주제를 벗어난 프로젝트로 보일 수 있어요. 다행히 초안에 이미 Validation, Join Guard가 있어서 거기에 복구 로직만 얹으면 됩니다.

장애 상황	감지	복구
기상청 API 타임아웃·오류	응답 지연, 5xx	재시도 3회 → 마지막으로 받은 예보(캐시) 사용
쉼터 API 오류	응답 실패	미리 받아둔 쉼터 CSV 파일로 대체
LLM 출력 형식 깨짐	JSON 스키마 검사 실패	재요청 → 그래도 실패하면 정해진 문구 템플릿으로 대체
프로필 정보 누락	필수 항목 없음	취약도를 "상"으로 간주하고 진행

이 주제의 좋은 점은 **"안전 서비스는 장애가 나도 조용히 멈추면 안 된다"**는 명분이 생긴다는 거예요. 장애 시에는 항상 더 보수적인 쪽(알림을 보내는 쪽)으로 판단한다는 원칙을 하나 정해두면 발표에서 기획 의도가 분명해집니다.

그대로 둬도 되는 것

병렬 조사 → 취합 → 핸드오프 → 작성·요약 구조, Handoff Guard로 불필요한 알림을 거르는 설계, 어르신용/보호자용 출력 분리는 가이드와 충돌하지 않고 오히려 "역할을 나눈 이유"를 설명하기 좋습니다.

시연 팁

Streamlit 화면에 "기상청 API 장애 주입" 체크박스를 하나 두세요. 켜면 일부러 API 호출을 실패시키고, 화면이나 로그에서 재시도 → 캐시 사용 → 정상 알림 전달 과정이 보이게 하면 가이드의 시연 순서(장애 발생 → 감지 → 복구 → 결과 전달)를 그대로 보여줄 수 있습니다.

최대한 가볍게 가는 기준으로 정리하면 이렇습니다.

```
[Streamlit]  ──HTTP──▶  [FastAPI]
 화면, 장애주입 체크박스      │

                     ▼                 ▼
               [MCP 서버]          [SQLite]
            날씨·쉼터 도구        캐시, 실행 로그
                     │
                     ▼
              기상청 / 쉼터 API
```

컨테이너는 **Streamlit, FastAPI 두 개**만 띄우고 docker-compose로 묶으면 끝이에요.

## 각 구성요소

**프런트엔드: Streamlit**
- 프로필 선택(테스트 인물 3~4명), 실행 버튼, 어르신용/보호자용 카드
- "기상청 API 장애 주입" 체크박스 → 요청에 `fault=weather` 같은 값만 실어 보냄
- 실행 로그(재시도·캐시 사용 여부)를 화면 아래에 표로 보여주면 시연이 쉬워집니다.

**백엔드: FastAPI**
- 엔드포인트는 세 개면 충분해요.
  - `POST /alert`: 프로필 받아서 전체 흐름 실행, 결과 반환
  - `GET /health`: 상태 확인 (배포 보고서용)
  - `GET /logs`: 최근 실행 기록 조회
- 에이전트 흐름은 LangGraph를 써도 되고, 가볍게 가려면 그냥 파이썬 함수 + `asyncio.gather`로 병렬 실행해도 충분합니다.

**MCP: 서버 하나, 도구 두 개**
- `get_weather(nx, ny)`, `get_shelters(lat, lon, season)`
- 재시도·캐시 폴백을 **이 도구 안에** 넣으면 에이전트 코드는 단순해지고, "장애 복구 계층"으로 설명하기도 좋아요.
- 수업에서 MCP가 필수가 아니라면, 처음엔 일반 파이썬 함수로 만들고 나중에 MCP로 감싸는 순서를 추천합니다. (FastMCP 쓰면 데코레이터만 붙이면 돼요.)

**DB: SQLite 하나**
- 별도 서버가 필요 없어서 가장 가벼워요. 테이블은 세 개면 됩니다.
  - `cache`: 마지막으로 성공한 날씨·쉼터 응답 + 저장 시각
  - `run_logs`: task_id, 에이전트, 시도 횟수, 에러, 복구 방법, 소요 시간
  - `profiles`: 테스트용 가상 인물
- `run_logs`만 잘 쌓아두면 가이드가 요구하는 **자동 복구율, 평균 복구시간**을 쿼리 한 줄로 뽑을 수 있어요.

**외부 API**
| 용도 | API                        | 장애 시 대체                   |
| ---- | -------------------------- | ------------------------------ |
| 날씨 | 기상청 단기예보            | SQLite 캐시                    |
| 특보 | 기상청 기상특보            | 없으면 기온 기준으로 자체 판정 |
| 쉼터 | 행정안전부 무더위·한파쉼터 | 미리 받아둔 CSV                |
| LLM  | 쓰는 모델 하나             | 재요청 → 고정 문구 템플릿      |

## 이것만은 지키세요

- API 키는 `.env`에 넣고 깃에 올리지 않기 (가이드 체크리스트 항목)
- 모든 실행에 `task_id`를 붙여서 로그에 남기기
- 장애 주입은 실제로 API를 끊지 말고 **코드에서 일부러 예외를 던지는 방식**으로 (시연 중에 안전함)

## 첫날 꼭 같이 정할 것

나눠서 개발하려면 **주고받는 데이터 형식**부터 합의해야 해요. 이게 없으면 통합 날 다 깨집니다.
- SafetyResearchResult, AlertResult의 JSON 형식 (1번이 초안 작성)
- MCP 도구의 입력·출력 형식 (2번)
- `run_logs` 테이블 컬럼 (3번)

그 전까지는 각자 **가짜 데이터(목업)**로 개발하면 서로 기다릴 필요가 없어요. 예를 들어 4번은 날씨 API가 완성되기 전에 고정된 JSON으로 Writer를 테스트하면 됩니다.



**팁**: 3번(AutoHealing)이 이 프로젝트의 평가 핵심이라, 통합 이후에는 다른 팀원들도 장애 시험을 같이 돕는 게 좋아요. 그리고 시연 영상은 미리 찍어둘 수 있으니 12일까지 꼭 확보해 두세요. 당일 API가 실제로 죽어도 영상으로 대체할 수 있습니다.
