# 로컬 시연 흐름 및 저장 안전성 검증 (2026-09-30)

## 2026-10-02 상담 복원 보완

브라우저 새로고침 뒤 로그인은 복원되지만 Redis의 진행 상담은 자동 조회하지 않아 질문·답변이 화면에서 사라지는 문제를 확인했습니다. 사용자별 최초 상담 진입에 기록을 한 번 조회하고 일반 화면 재실행에는 반복 조회하지 않도록 보완합니다. 조회 실패 시 자동 반복 호출 대신 수동 새로고침으로 복구하며, 기록 확인 전에는 새 질문·저장·종료를 막습니다. 이미 표시된 기록은 수동 조회 실패로 삭제하지 않습니다. 다른 탭의 이후 변경은 기존 ‘진행 대화 새로고침’으로 확인합니다.

AppTest는 초기 복원·단일 조회·사용자 전환·조회 실패 후 복구와 기존 상담 흐름을 검사합니다. Redis TTL이 지난 기록은 복원할 수 없으며 진행 상담 복원은 영구 보관과 다릅니다.

## 실행 환경

로컬 Supabase(54321), FastAPI(18000), 사용자 화면(18501), 관리자 화면(18502),
프로젝트 전용 Redis(16379)를 사용했습니다. 시작 방법은 [로컬 실행 안내](database_step3.md)를 따릅니다.
실제 `.env`의 클라우드 주소와 키를 변경하지 않았습니다.

공고 저장에 필요한 새 함수는 `supabase/migrations/20260930000100_atomic_listing_save.sql`에 있습니다.
기존 로컬 DB에는 `supabase migration up --local`로 적용합니다.
클라우드에는 아직 적용하지 않았으므로, 클라우드에서 이번 버전의 공고 생성·수정을 실행하려면
같은 SQL을 먼저 적용해야 합니다. 빈 DB의 수동 설치용 `bootstrap_portfolio.sql`에도 포함했습니다.

## 키 없는 자동 등록 시연

1. 관리자 로그인 후 **청약정보 등록(자동)**을 엽니다.
2. **가상 샘플 재생 → 가상 분석 결과 불러오기**를 선택합니다.
3. 월세 누락 때문에 **등록 가능 0건 / 확인 필요 1건**이 표시됩니다.
4. 샘플 기준값 **280000**을 입력하고 **이 값으로 다시 확인**을 누릅니다.
5. 등록 가능 1건과 금액·기간을 확인한 뒤 등록합니다.
6. 관리자 목록과 사용자 화면에서 시연용 공고를 확인합니다.

샘플은 저장된 가상 분석 결과이며 외부 AI를 호출하지 않습니다. 임의 업로드 문서를 분석한 결과가 아닙니다.
날짜는 2026-10-01~2026-10-31로 고정되어 있고 원문 링크는 실제 신청 페이지가 아닙니다.
실제 분석은 **Gemini로 실제 문서 분석**을 선택하고 키를 설정해야 합니다.
두 모드 모두 기존 `validate_all` 검증과 관리자 등록 API를 사용합니다.

이번에는 Gemini 호출을 하지 않았으므로 실제 문서 추출의 정확도·시간·호출 비용은 미측정입니다.
가상 샘플에서 확인한 것은 값 누락을 검출하고 관리자가 수정해 등록할 수 있다는 점입니다.
성공한 항목은 같은 분석 묶음의 재시도에서 제외합니다. 브라우저를 닫거나 같은 문서를 다시 분석하는 경우까지
중복을 차단하는 서버 등록 식별자와 실제 문서 5~10개의 정답 기반 평가는 후속 과제입니다.

## 리팩토링 마무리 검증 (2026-10-01)

상담·생활권 화면을 기능별 모듈로 나누고 두 화면의 공통 JSON 응답 해석을 묶었습니다.
사용자 계정이 바뀌면 이전 사용자의 상담과 안내 메시지를 초기화합니다.
새 회귀 테스트는 상담 전송 실패→재시도, 종료 취소, 사용자 전환, 주소 없는 공고의
외부 지도 호출 차단, 검색어 정규화, 잘못된 API JSON 구조, 요약 선택·삭제 취소를 확인합니다.

기존 환경과 별도로 `.env`가 없는 소스 사본과 앱별 새 가상환경에서 requirements를 설치했습니다.
백엔드 199개, 관리자 342개, 사용자 168개, 총 709개가 통과했습니다.
PR 자동 검사의 명령도 이 설치·검사 방식이며 GitHub Actions 자체 실행 결과는 아직 미확인입니다.
브라우저에서는 임시 로컬 계정으로 모의 상담 응답, 대화 종료 취소, 요약 미리보기 저장,
가상 공고 검색의 상세주소 누락 안내를 확인했습니다. 실제 Gemini나 Kakao 분석은 하지 않았습니다.

## 녹화 리허설 순서 (약 5분)

1. 로컬 Supabase와 Redis, 백엔드·사용자·관리자 화면을 실행합니다.
   실행 방법과 설정은 `docs/database_step3.md`의 기존 안내를 사용합니다.
   시연 데이터의 신청 기간이 지나면 기존 시드 스크립트 안내에 따라 기준일을 갱신합니다.
2. 사용자 화면에서 자치구·금액 조건을 검색하고 페이지를 이동합니다.
   설명: “필요한 공고만 서버에서 페이지 단위로 받아 보여 줍니다.”
3. 관리자 자동 등록에서 가상 샘플의 누락 금액을 보정합니다.
   설명: “AI가 만든 값도 그대로 저장하지 않고 검증하고 수정합니다. 지금은 가상 결과 재생입니다.”
4. 시연용 공고를 등록한 뒤 사진을 추가하고 수정한 내용을 사용자 화면에서 확인합니다.
   설명: “공고와 사진 정보는 함께 저장하고, 실패하면 새 업로드를 정리합니다.”
5. 로그인한 사용자로 상담 질문을 입력하고 요약을 저장·조회합니다.
   설명: “현재 답변은 로컬 모의 응답이며 실제 AI 정확도를 보여 주는 장면은 아닙니다.”
   기본 preview 요약은 서버 재시작 시 사라집니다. 영구 DB 저장을 보여 주려면 기존 설정 안내를 따릅니다.
6. 테스트 결과와 변경 전후 코드 구조를 보여 줍니다.
   설명: “화면·저장 처리·공통 코드를 분리하고 자동 검사로 기존 기능을 확인했습니다.”

가상 시드 공고에는 상세주소가 없으므로 생활권 지도 성공 장면 대신 주소 누락 안내를 보여 줄 수 있습니다.
지도 성공 장면을 넣으려면 별도 검증용 공고에 공개 주소를 넣고 Kakao 연결을 직접 확인해야 합니다.
키·비밀번호·환경설정 파일은 녹화에 포함하지 않습니다. 영상 녹화 자체는 아직 수행하지 않았습니다.

새 세션에서 생활권 주소로 바로 접속할 때 Streamlit의 Page not found 안내가 한 번 표시됐지만 화면은 로딩되었습니다. 녹화는 루트 홈 주소에서 사이드바 메뉴로 이동하세요. 직접 주소 접속의 초기 안내 개선은 후속 확인 대상입니다.

## 속도 개선 1~6단계 검증 (2026-10-01)

1. 변경 전 기준: main의 `13ce23e`와 동일한 로컬 가상 데이터로 측정했습니다.
2. 반복 호출 제거: 사용자별 세션에 상담 목록·닉네임 60초, 생활권 분석 300초를 저장합니다. 실패는 저장하지 않습니다. 저장·삭제·계정 전환·새 검색·새로고침과 만료 시 다시 조회합니다.
3. 생활권 검색: 전체 공고 다운로드 대신 DB에서 제목·주택명·지역·주소를 검색하고 20건씩 받습니다. 공백·대소문자·NFKC 정규화와 `%`, `_`의 문자 검색을 유지합니다.
4. 지도 요청: HTTP 연결을 재사용하고 세 시설 종류를 동시에 조회합니다. 프로세스당 작업자·연결은 최대 3개, 대기 포함 분석 그룹은 6개로 제한합니다. 한 종류라도 실패하면 부분 결과를 정상 결과로 저장하지 않습니다.
5. DB 개선: 검색 GIN 인덱스와 즐겨찾기 공고 ID 인덱스를 추가하고 순위 집계를 SQL로 옮겼습니다. 검색 실행계획에서 GIN 인덱스 사용을 확인했습니다. 검색어·데이터 규모에 따라 DB가 다른 실행계획을 선택할 수 있습니다.
6. 재측정: 아래 수치와 재현용 스크립트, 회귀 검증을 남겼습니다.

API는 공고 1,000건·즐겨찾기 800건의 가상 자료, 검색 결과 10건, 순위 100건으로 각각 30회 측정했습니다. 변경 전·후 순서로 같은 머신에서 연결을 재사용하고 예열했으므로 실서비스 부하·콜드 스타트 비교가 아닙니다. 시설·화면 비교는 모의 응답이며 실제 Kakao 속도·한도 검증이 아닙니다. 병렬화는 요청 개수를 줄이지 않습니다. 순위 API 응답 크기는 동일하며 감소한 것은 DB에서 백엔드로 전달하는 데이터입니다.

외부 연결을 차단한 자동 테스트 719개(백엔드 204, 관리자 342, 사용자 173)가 통과했습니다. 캐시 만료·사용자 분리·실패 후 재시도, 새로고침·저장 후 갱신, 후보 페이지 이동, 동시 시작·결과 순서·오류 전파, 실제 로컬 HTTP 연결 재사용을 검사했습니다. SQL 검증은 페이지 중복·검색 정규화·문자 검색·순위 집계·RPC 권한을 실제 로컬 DB에서 확인하고 롤백합니다.
